### Current `src/hooks/useFormStackViewport.ts` (compiles, but RUNTIME-leaks)
```ts

import type { FormStackViewportValue } from '../types';

```
Why it compiles today: `FormStackViewportContextValue` is assignable to the sanitized
`FormStackViewportValue` because `InternalStackEntry extends StackEntry` (array
covariance) and the extra `onCancelRequest` is allowed on assignment (not an object
literal). So the *type* is fine but the *runtime object* still carries `component`,
`deferred`, `confirmOnCancel`, `onCancelRequest`. S2 closes the RUNTIME leak.

### Target hook body (from work item §3a + issue_analysis.md step 4)
```ts
import { useContext, useMemo } from 'react';
import { FormStackViewportContext } from '../context';
import type { FormStackViewportValue } from '../types';
/** [REWRITTEN JSDoc — Mode A: sanitized surface, drop spread/assignable claim] */
export function useFormStackViewport(): FormStackViewportValue | null {
  const internal = useContext(FormStackViewportContext);
  return useMemo(() => {
    if (!internal) return null;
    return {
      stack: internal.stack.map(({ id, label }) => ({ id, label })),
      onClose: internal.onClose,
    };
  }, [internal]);
}
```
- `useMemo` deps `[internal]`: the context value identity changes when the provider's
  `viewportValue` useMemo recomputes (on stack/onClose/onCancelRequest change). When
  unchanged, `internal` is referentially stable → memo returns the same projected
  object → no needless consumer re-render. Correct, matches issue_analysis.md.
- The `.map(({ id, label }) => ({ id, label }))` produces NEW plain objects carrying
  ONLY `{ id, label }` — `component`, `deferred`, `confirmOnCancel` are dropped at runtime.

## 6. Why conditional-type guard is the right pattern for "not assignable"

You cannot write `expect(X).not.toAssignTo(Y)` — assignability is compile-only. The
conditional-type + literal-const idiom encodes the assignability question as a literal
type (`true`/`false`) that is BOTH:
- a compile-time check (assigning the wrong literal to a `true`/`false`-typed const is a
  TS error → test fails to compile on regression), and
- a runtime value (assertable with `expect(...).toBe(true|false)`).

This is the established TS "negative assignability test" pattern.
